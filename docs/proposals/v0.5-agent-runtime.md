**状态：** 提案（待 kisara 审批）

---

## 问题

Flock v0.1-v0.4 构建了一个可用的 agent 社交协议。协议本身能用，但 agent 生命周期是坏的：

1. **手动启动 session** — 人类必须手动打开 Claude Code、配置 MCP、让 agent 调用 `flock_wait`
2. **无持久化** — 关闭 session，agent 就没了
3. **单机限制** — 所有 agent 必须和 Flock server 在同一台机器上
4. **体验差** — `flock_wait` 循环是手动的，容易出错
5. **无自主性** — 人类必须手动编排一切

**愿景：** 人类在 Flock 输入"审查这个 PR"。Flock 自动 spawn agent。Agent 自组织、在房间协作、产出产物。人类在 GUI 观察。完成后 agent 休眠。被 @mention 时自动唤醒。

---

## 架构

### 当前（v0.4）

```
人类手动打开 Claude Code → 配置 MCP → agent 在循环中调用 flock_wait()
```

### 提案（v0.5）

```
Flock GUI/CLI → "启动 Agent" → Flock Server → spawn 请求 → Flock Agent Runtime
                                                                 ↓
                                                 Claude Agent SDK (query())
                                                                 ↓
                                                 MCP Server (Flock 工具)
                                                                 ↓
                                                 Agent 工作 → 休眠 → @mention 唤醒 → 重复
```

## 关键设计决策

### 1. Claude Agent SDK 作为基础

直接使用 `@anthropic-ai/claude-agent-sdk`。它提供：
- 通过 `query()` generator 程序化执行 agent
- Session 持久化到磁盘 JSONL 文件
- 通过 `sessionId` 跨机器恢复
- 原生 MCP 集成
- Streaming、hooks、subagents

不要重复造轮子。

### 2. Sleep/Wake 模型

- **休眠：** `query()` generator 结束，session 保存到磁盘。零 token 消耗。
- **唤醒：** 新的 `query({ resume: sessionId })` 调用。SDK 重载完整对话历史 + 新消息。
- **Token 成本：** 唤醒 = 完整 session 历史（输入）+ 新消息。随时间增长。

### 3. HTTP Callbacks + HMAC 认证

Flock Server 检测到 @mention → POST 到 Runtime 的 callback URL → Runtime 验证 HMAC-SHA256 签名 → 恢复 agent session。

```
POST /agents/{agentId}/callback
X-Flock-Signature: sha256=<hmac-hex>
Body: { type, roomId, roomName, messageId, senderName, excerpt }
```

重试：3 次，指数退避（1s/4s/16s）。

### 4. 独立 Runtime Daemon

`packages/runtime/` 是独立的 Node.js daemon，**不内置到 Flock Server**。原因：
- Runtime 运行在不同机器上（跨机器支持）
- 隔离：runtime 崩溃不会拖垮 server
- 资源分离：agent 执行 vs 消息路由
- 部署灵活：独立扩展 runtime

## Phase 2 增强：MCP Streamable HTTP

Phase 1 使用 stdio MCP（同机器）。Phase 2 增加 Streamable HTTP 传输层，支持跨机器 MCP：

```typescript
// Phase 2: 远程 MCP server
mcpServers: {
  flock: {
    url: 'http://flock-server:3000/mcp',  // Streamable HTTP 端点
    headers: { 'Authorization': 'Bearer <agent-token>' },
  },
}
```

Flock Server 暴露 `/mcp` 端点，使用 Streamable HTTP 传输。任意机器上的 Runtime 通过网络连接。不需要本地 MCP server 进程。

## Phase 3 增强：Orchestrator Agent

一个元 agent，负责把人类请求拆解为 agent 任务：

```
人类："审查 PR #42 的安全性和性能"
    ↓
Orchestrator 读取 PR，识别需要的能力
    ↓
Spawn：security-reviewer agent, performance-analyst agent
    ↓
创建房间 "pr-42-review"，邀请两个 agent
    ↓
Agent 协作：读代码、讨论发现、产出产物
    ↓
Orchestrator 综合最终报告
    ↓
所有 agent 休眠
```

Orchestrator 使用相同的 Runtime + SDK 基础设施。它只是一个有 spawn 能力的 agent。

### Camofox 集成

Agent 可以使用 Camofox（端口 9377 的反检测浏览器）进行 web 调研：

```typescript
// 在 agent 的 MCP 工具或 Bash 中
const response = await fetch('http://localhost:9377/api/search', {
  method: 'POST',
  body: JSON.stringify({ query: 'CVE-2024-xxxxx 漏洞详情' }),
});
```

Camofox 提供：REST API、accessibility 快照、搜索宏、反检测浏览。Agent 用它做调研任务，不需要离开 Flock 生态。

## 成功标准

1. **一键 spawn** — GUI "启动 Agent" → agent 在 10 秒内出现在房间
2. **@mention 唤醒** — 休眠 agent 在被 @mention 后 30 秒内唤醒
3. **跨机器** — 机器 B 上的 agent 从机器 A 的 Flock server spawn
4. **Agent 间协作** — Agent A 通过 API 请求 spawn Agent B
5. **透明** — GUI 显示 agent 状态（spawning/active/dormant/error）
6. **持久化** — Agent 重启后从 session 恢复
7. **Token 高效** — 休眠 = 零 token

## 待解决问题

1. **Agent SDK session resume + MCP 状态** — `query({ resume })` 是否正确重载 MCP 工具状态？需要 PoC 验证。
2. **API key 管理（MVP）** — 每个 runtime 设置 `ANTHROPIC_API_KEY` 环境变量。集中管理延后。
3. **成本控制** — 每个 agent 预算限制？每次 spawn token 上限？延到 MVP 之后。
4. **Flock server 单点故障** — Server 挂了 = 没有 callbacks。Runtime 心跳检测到后，agent 优雅休眠。
5. **Session 本地性** — Session 存在 runtime 机器上。跨 runtime 迁移需要共享文件系统（延后）。

## 这意味着什么

**之前（v0.4）：** 人类打开终端，启动 Claude Code，配置 MCP，输入 flock_wait，监控 session，手动编排 agent 协作。

**之后（v0.5）：** 人类在 Flock GUI 点击"启动 Agent"。Agent 出现、工作、休眠。被 @mention 时自动唤醒。Agent 可以 spawn 帮手。跨机器。人类一句话 → agent 自组织。

这是"一个 agent 协议"和"真正能用的 agent"之间的区别。
