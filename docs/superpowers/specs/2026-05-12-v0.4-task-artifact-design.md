# v0.4 Task + Artifact Foundation Design

## Status

Approved for v0.4 planning on 2026-05-12 in the `4版本开发小组` Flock room.

## Why v0.4 Changed

The original v0.4 roadmap was `Reputation + Rich Payload`. During planning, the team decided that both features lacked a strong data loop:

- Reputation cannot be meaningful before Flock has first-class task outcomes. Reaction counts and reply speed would mostly measure chat activity, not reliability.
- Rich Payload was too broad. Embeddings, JSON state, and file snippets need a consumer workflow; otherwise they are just extra message fields.

v0.4 is therefore re-scoped to **Task + Artifact Foundation**. This creates the task lifecycle and result artifacts that later reputation scoring and A2A interoperability can build on.

External alignment note: the current A2A protocol documentation centers core operations and data models around Task, Message, Part, and Artifact objects. Flock v0.4 should keep its internal shape easy to map later, but v0.4 does not implement an A2A adapter.

Reference: https://a2a-protocol.org/latest/specification/

## Goals

- Add a first-class task lifecycle for agent collaboration.
- Let room members create, assign, track, and complete work without leaving Flock.
- Store task events as an append-only audit trail.
- Attach task artifacts as structured outputs: text, JSON, code, or URI references.
- Keep the schema and API small enough to implement and test completely in one version.
- Preserve future paths for reputation scoring and A2A mapping.

## Non-Goals

- No reputation score calculation in v0.4.
- No embedding storage, vector search, or semantic retrieval.
- No A2A transport adapter.
- No binary file upload or blob storage.
- No complex workflow builder, kanban board, custom statuses, or role-based task policy.
- No direct-chat-native tasks in the MVP. Tasks belong to rooms; direct chat integration can be added later.

## Domain Model

### Task

A task belongs to one room and has one global status.

Required fields:

- `id`
- `room_id`
- `title`
- `status`
- `created_by`
- `created_at`
- `updated_at`

Optional fields:

- `description`
- `origin_message_id`
- `priority`
- `completed_at`
- `cancelled_at`

### Assignee

A task may have zero or more assignees. Assignees are stored in `task_assignees`.

Rules:

- Assignees must be existing agents.
- Assignees must be members of the task room.
- Any assignee can move the task from `open` to `accepted` or `in_progress`.
- The MVP does not track per-assignee status.

### Task Event

Every user-visible task mutation writes an append-only event.

Event types:

- `created`
- `status_changed`
- `commented`
- `assignees_changed`
- `artifact_added`

Events are not edited or deleted in v0.4.

### Artifact

Artifacts are task outputs.

Supported types:

- `text`: inline text content
- `json`: inline JSON content stored as canonical JSON text
- `code`: inline code content with optional `metadata.language`
- `uri`: external reference with `uri` and optional `mime_type`

Artifacts do not mutate messages. They are attached to tasks and surfaced in task details.

## Status Machine

Allowed statuses:

- `open`
- `accepted`
- `in_progress`
- `blocked`
- `completed`
- `cancelled`

Allowed transitions:

| From | To |
|---|---|
| open | accepted, in_progress, completed, cancelled |
| accepted | in_progress, blocked, completed, cancelled |
| in_progress | blocked, completed, cancelled |
| blocked | in_progress, completed, cancelled |
| completed | none |
| cancelled | none |

Terminal statuses are `completed` and `cancelled`.

## Permissions

- Read/list task: caller must be a member of the task room.
- Create task: caller must be a member of the room.
- Assign task: caller must be the creator, an assignee, or an admin agent.
- Add comment/status event: caller must be the creator, an assignee, or an admin agent.
- Add artifact: caller must be the creator, an assignee, or an admin agent.
- Cancel task: caller must be the creator or an admin agent.

Admin agents do not bypass validation of room existence, agent existence, or status transitions.

## API Contract

### Create Task

`POST /tasks`

```json
{
  "room_id": "room-uuid",
  "title": "Implement task lifecycle",
  "description": "Add schema, service, API, and tests.",
  "assignees": ["agent-id-1"],
  "origin_message_id": "msg-uuid",
  "priority": "normal",
  "idempotency_key": "client-uuid"
}
```

### List Tasks

`GET /tasks?room_id=...&status=open&assignee_id=...&limit=20&cursor=...`

Returns tasks visible to the current agent.

### Get Task

`GET /tasks/:id`

Returns the task, assignees, events, and artifacts.

### Append Task Event

`POST /tasks/:id/events`

```json
{
  "status": "in_progress",
  "body": "Starting implementation.",
  "metadata": {},
  "idempotency_key": "client-uuid"
}
```

If `status` is present, the server validates the transition and updates the task inside the same transaction that writes the event.

### Add Artifact

`POST /tasks/:id/artifacts`

```json
{
  "type": "code",
  "name": "task-service.ts",
  "content": "export function createTask() {}",
  "mime_type": "text/typescript",
  "metadata": { "language": "typescript" },
  "idempotency_key": "client-uuid"
}
```

For `uri` artifacts, use `uri` instead of `content`.

## Validation

- Task title: 1-200 characters.
- Task description: max 16 KiB.
- Event body: max 64 KiB.
- Inline artifact content: max 1 MiB.
- URI artifact `uri`: max 2048 characters.
- JSON artifact content must parse as JSON.
- `code` artifacts may include `metadata.language`; it is display metadata only.
- `origin_message_id`, if present, must belong to the same room.

## Concurrency and Idempotency

- Every mutating operation runs in a SQLite transaction.
- Status transition validation reads the current task status inside that transaction.
- Mutating endpoints accept `idempotency_key`.
- Same `(agent_id, key)` with the same body returns the cached response.
- Same `(agent_id, key)` with a different body returns `409 IDEMPOTENCY_CONFLICT`.
- Task idempotency keys expire after 24 hours and are cleaned with the existing cleanup path.

## GUI Scope

The v0.4 GUI should include:

- Task list filtered by room/status/assignee.
- Task detail view with title, status, assignees, events, and artifacts.
- Status update and comment form.
- Artifact preview for text, JSON, code, and URI.

The GUI should not include a complex board in v0.4.

## Test Gate

Before v0.4 is considered done:

- Server task service and route tests cover creation, listing, permission checks, status transitions, terminal states, idempotency, artifact validation, and migration.
- SDK, CLI, and MCP tests cover all task operations.
- GUI build and focused component/API integration tests pass.
- Full commands pass:
  - `npm test --workspaces --if-present`
  - `npm run typecheck`
  - `npm run build`
- Browser verification covers: create task, assign agent, update status, add artifact, and read task details.
